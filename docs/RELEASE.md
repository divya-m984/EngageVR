# EngageVR — Release Procedure

## What a release of this repository is

A tagged, reproducible snapshot of a **research software prototype**.

It is not a product release. It is not a deployment. It carries no
validated model, no scientific finding, and no clinical, diagnostic, or
psychological claim. Every metric the software produces came from
synthetic data generated by this repository, and every artifact says so.

> Reproducibility is not validity. Tracking is not validation.
> Registration is not approval. Packaging is not production readiness.
> Drift alerts are engineering diagnostics.

Tagging a release does not change any of that.

## Who runs this

The repository owner. **The assistant does not create tags, does not push,
and does not create GitHub Releases.** Steps 12 and 13 below are written
as instructions to be executed by a person, and they are the only steps
that write to Git or to GitHub.

Automating GitHub Release creation is deliberately out of scope: the
PROJECT_PLAN asks for *release instructions*, not a release robot.

## 1. Clean checkout

Work from a fresh clone, not from a working tree that has been
accumulating state.

```bash
git clone git@github.com:divya-m984/EngageVR.git engagevr-release
cd engagevr-release
git status                       # must be clean
git log --oneline -5
```

Nothing under `artifacts/`, `mlruns/`, `models/`, or `data/` should
exist. Their absence is the point: the release must reproduce from
source.

If you must verify from an uncommitted working tree, copy the source into
a temporary directory excluding `.git`, `.venv`, `artifacts`, `mlruns`,
and every cache, and run the checks there. **Never** use `git clean`.

## 2. Dependency verification

```bash
uv --version                     # 0.11.32 or newer
uv lock --check                  # the lock and pyproject.toml agree
uv sync --locked                 # install exactly what the lock pins
uv tree | head -40               # eyeball the direct dependency set
```

`uv lock --check` failing means `pyproject.toml` changed without the lock
being regenerated. Fix that before anything else: every later step, the
Docker builds included, installs from this lock.

Confirm the two Milestone 10 dependencies and nothing unexpected beside
them:

```bash
uv pip list | grep -Ei '^(mlflow|dvc) '
```

Expect `mlflow-skinny` and `dvc`. If `mlflow` (the full distribution)
appears, pandas has been downgraded across a major version; see
`docs/MLOPS.md` §2.

## 3. Full checks

```bash
uv run ruff format --check src tests
uv run ruff check src tests
uv run mypy src
uv run pytest
uv run pre-commit run --all-files
```

`uv run pytest` runs the whole suite including `tests/system/`. Two
suites stay skipped because they are opt-in:

```bash
ENGAGEVR_RUN_HARDWARE_TESTS=1 uv run pytest -m hardware       # needs a webcam
ENGAGEVR_RUN_DVC_SYSTEM_TESTS=1 uv run pytest -m dvc_system   # ~6 minutes
```

A hardware run is **not** a release requirement — no webcam is assumed.
The DVC two-tree proof **is** worth running before a release; step 4
covers the same invariant more cheaply. Do not report either skipped
suite as a pass.

## 4. DVC reproducibility

```bash
uv run dvc dag
uv run dvc repro
uv run dvc status                # expect: Data and pipelines are up to date
uv run dvc repro                 # expect: every stage "didn't change, skipping"
```

Then verify the lock is **byte-stable across a fresh reproduction** — the
invariant this pipeline maintains:

```bash
sha256sum dvc.lock
rm -rf artifacts/pipeline
uv run dvc repro
sha256sum dvc.lock               # must be the SAME digest
git status --porcelain dvc.lock  # must be empty
```

A modified `dvc.lock` here is a **failure**, not expected churn. It means
a declared output stopped being byte-stable; find it before releasing.
See DEC-100 and DEC-104.

Optionally run the two-source-tree proof (about six minutes):

```bash
ENGAGEVR_RUN_DVC_SYSTEM_TESTS=1 uv run pytest -m dvc_system
```

Then verify **logical** reproducibility across two independent
executions:

```bash
cp artifacts/pipeline/mlops/reproducibility.json /tmp/engagevr-first.json
rm -rf artifacts/pipeline
uv run python -m engagevr mlops-demo
uv run python -m engagevr repro-manifest \
  --output /tmp/engagevr-second.json \
  --compare /tmp/engagevr-first.json
```

Exit code 0 means the two executions agree on every dataset fingerprint,
run identifier, model-version identifier, report fingerprint, and
byte-deterministic checksum. Timestamps and MLflow identifiers are
excluded from identity by construction and are not compared; see
`docs/MLOPS.md` §7.

A non-zero exit lists each difference. Investigate before releasing.

## 5. MLflow tracking check

```bash
uv run python -m engagevr mlflow-log \
  --run artifacts/pipeline/experiments/baseline-engagement_class \
  --run artifacts/pipeline/experiments/uncertainty-engagement_class \
  --output artifacts/pipeline/mlops/mlflow_runs.json
```

Confirm in the printed output and in the written summary:

- the tracking URI is `file://…/mlruns` — **local, no server**;
- `is_synthetic: true`;
- `scientific_evaluation_eligible: false`;
- `registered model: none`;
- the metric count is non-zero and `skipped metrics` is accounted for.

Then confirm nothing leaked into a run directory:

```bash
find artifacts/pipeline/experiments -name 'mlruns' -o -name 'MLmodel' -o -name 'meta.yaml'
# expect: no output
```

`mlruns/` is gitignored and is not part of the release.

## 6. Model and artifact manifest validation

```bash
uv run python -m engagevr model-manifest \
  --run artifacts/pipeline/experiments/baseline-engagement_class \
  --output artifacts/pipeline/mlops/model_versions \
  --verify
```

`--verify` re-hashes every referenced artifact and exits non-zero on any
mismatch. Confirm in the output:

- every line ends `eligible=false`;
- the closing sentence "No version here is production, staging, champion,
  approved, or validated" is printed;
- the model-version identifiers are unchanged from the previous release
  **only if** the dataset, split, feature schema, configuration, and code
  version are all unchanged. A changed identifier is not a fault; it is the
  mechanism working.

## 7. Docker builds

```bash
docker compose config                       # validate without building
docker build -f Dockerfile.backend   -t engagevr-backend:local .
docker build -f Dockerfile.dashboard -t engagevr-dashboard:local .
```

Then confirm nothing generated or private is inside either image:

```bash
for image in engagevr-backend:local engagevr-dashboard:local; do
  docker run --rm --entrypoint python "$image" -c "
import pathlib
root = pathlib.Path('/app')
bad = [str(p) for p in root.rglob('*')
       if '.venv' not in p.parts and p.is_file()
       and (p.suffix in {'.joblib', '.pkl', '.parquet', '.jsonl', '.mp4', '.npy'}
            or p.name in {'.env', 'CLAUDE.local.md', 'dvc.lock'}
            or 'mlruns' in p.parts or 'experiments' in p.parts)]
print(sorted(p.name for p in root.iterdir()), 'suspicious:', bad)
"
done
```

Expect an empty `suspicious:` list, and a top level of `.venv`, `src`,
`configs`, `pyproject.toml`, `README.md`, `artifacts` (empty mount
points), plus `protocol` in the backend.

## 8. Backend health smoke

```bash
mkdir -p artifacts/sessions artifacts/experiments
docker compose up -d
docker inspect --format '{{.State.Health.Status}}' engagevr-backend    # wait for: healthy
curl -sS http://127.0.0.1:8000/health
curl -sS http://127.0.0.1:8000/version
```

`/health` returns `{"status":"ok",…}`. `/version` reports the package
version, the protocol version, and the scope and security notes — read
them; they are the statement that this backend produces no engagement
estimate and has no authentication.

## 9. Dashboard smoke

```bash
docker inspect --format '{{.State.Health.Status}}' engagevr-dashboard   # wait for: healthy
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8501/_stcore/health   # 200
```

Optionally open `http://127.0.0.1:8501` and confirm the provenance banner
and the synthetic labelling appear. Then stop everything:

```bash
docker compose down
docker ps -a --filter name=engagevr        # expect: no rows
```

Leave no container running.

## 10. Protocol drift

```bash
uv run python scripts/generate_protocol_artifacts.py
git diff --exit-code -- protocol/
```

Must produce **no drift**. If the protocol changed, stop: a protocol
change is a compatibility event for the Unity client and needs its own
justification, its own decision record, and its own version bump. It is
not something a release absorbs quietly.

## 11. Git status is clean

```bash
git status --porcelain
```

Must be empty. `mlruns/`, `artifacts/`, and `.dvc/tmp/` are ignored;
`dvc.lock` is tracked and byte-stable, so a full reproduction in step 4
leaves it unmodified.

**There is no expected exception here.** If `dvc.lock` appears modified
after step 4, a declared pipeline output has stopped being byte-stable.
Do not commit over it and do not `git checkout` it away: find the file
that moved. `tests/unit/test_dvc_determinism.py` and
`ENGAGEVR_RUN_DVC_SYSTEM_TESTS=1 uv run pytest -m dvc_system` will
localise it. See DEC-100, DEC-104, and `docs/MLOPS.md` §6.

## 12. Version and release preparation

`engagevr.__version__` in `src/engagevr/__init__.py` and `version` in
`pyproject.toml` are one value and must stay equal (a test asserts it).

Before tagging:

1. Decide the version. This is a research prototype at `0.1.0`. **A
   milestone is not a release**: reaching Milestone 10 is not a reason to
   go to `1.0.0`. Bump the patch or minor component.
2. Update both files to the same value.
3. Update `docs/PROGRESS.md` with the milestone status.
4. Re-run steps 3, 4, and 10 after the version change: the version
   participates in run identifiers and in every model-version identifier,
   so the fingerprints will legitimately change.
5. Commit.

```bash
make release-check
```

runs the automatable subset of steps 2–4 and 10 in one go. It does not
cover Docker (step 7–9), which needs a daemon.

## 13. Tag and release — instructions only

**Run these yourself. The assistant does not run them.**

```bash
# Confirm the tree is clean and the checks above passed.
git status
git log --oneline -1

# Annotated tag, on the commit that passed the checks.
git tag -a v0.1.1 -m "EngageVR 0.1.1 — research software prototype (Milestones 0-10)"

# Push the commit and the tag.
git push origin main
git push origin v0.1.1
```

If you create a GitHub Release, the description must state:

- that this is a **research software prototype**;
- that every metric it produces came from **synthetic data**;
- that **no validated participant-labelled engagement or cognitive-load
  dataset exists**, and no human-subject evaluation has taken place;
- that **no model is production-ready, approved, or validated**;
- that engagement and cognitive-load outputs are **estimates**, never
  medical, psychological, clinical, or diagnostic conclusions.

Do not attach a model binary, a dataset, a session recording, or a
tracking store to a release. They are gitignored for the same reasons
they should not be published.

## Release checklist

| # | Step | Command | Gate |
|---|---|---|---|
| 1 | Clean checkout | `git clone …` | tree clean, no `artifacts/` |
| 2 | Dependencies | `uv lock --check && uv sync --locked` | lock in sync |
| 3 | Full checks | `ruff`, `mypy`, `pytest`, `pre-commit` | all pass |
| 4 | DVC reproducibility | `dvc repro` ×2, `sha256sum dvc.lock` ×2, `repro-manifest --compare` | lock byte-identical; second repro no-op; identities match |
| 5 | MLflow | `mlflow-log` | local URI, synthetic, ineligible, nothing registered |
| 6 | Model versions | `model-manifest --verify` | no checksum mismatch |
| 7 | Docker builds | `docker build` ×2, image contents | no generated or private state |
| 8 | Backend health | `docker compose up -d`, `curl /health` | healthy, 200 |
| 9 | Dashboard health | `curl /_stcore/health` | healthy, 200 |
| 10 | Protocol drift | `generate_protocol_artifacts.py` + `git diff` | no drift |
| 11 | Git clean | `git status --porcelain` | empty, `dvc.lock` included |
| 12 | Version | edit, re-run 3/4/10, commit | versions equal |
| 13 | Tag and push | **owner only** | — |

---

## What a passing checklist means

That the software builds, installs from a lock file, reproduces its own
synthetic demo, packages into two images that answer their health checks,
and carries its provenance everywhere.

## What it does not mean

That any engagement estimate, cognitive-load estimate, uncertainty
interval, abstention decision, or adaptation proposal has been validated
against a human being. None has. That work needs participants, ethics
approval, and instruments this project does not yet have, and it is
Milestone 11 and beyond.
